INTRODUCCIÓN: MANUAL DE SUPERVIVENCIA

Si eres nuevo en esto, bienvenido. Antes de ver código, entendamos las herramientas que vamos a usar con analogías simples.

La "Santísima Trinidad" del Desarrollo

  • Flutter (El Pintor): Imagina que tienes una caja de LEGOs infinitos. Flutter son las piezas (llamadas Widgets). Botones, textos, columnas... todo son piezas visuales que "pintan" la pantalla.
  • Dart (El Cerebro): Las piezas de LEGO no se mueven solas. Dart es el lenguaje que les da vida. Es quien dice "Si toco este botón rojo (Flutter), entonces suena música (Lógica Dart)".
  • Firebase (La Mochila en la Nube): Tu móvil tiene poco espacio. Firebase es una mochila mágica de Google en internet donde guardamos las fotos de las canciones, los archivos MP3 y los datos de los usuarios.

Metáfora de Construcción

Esta guía está ordenada de forma lógica, como si construyéramos una casa. No te saltes pasos.

  1. Cimientos (Bloques 0-1): Preparamos el terreno (Configuración) y los planos (Modelos). Sin esto, la casa se cae.
  2. Fontanería (Bloque 3): Las tuberías por donde viaja el agua (Datos). Son los Servicios. Nadie los ve, pero son vitales.
  3. Electricidad (Bloque 5): El sistema de seguridad. Quién entra y quién sale (Autenticación).
  4. Decoración (Bloque 4 y 6): Pintura y muebles (Diseño y Widgets).
  5. Habitaciones (Bloque 7): Las estancias finales donde vive el usuario (Pantallas).

0.1 Requisitos Previos

Para ejecutar este proyecto, el entorno de desarrollo debe contar con:

  • Flutter SDK: (Versión Stable 3.x) añadido al PATH del sistema.
  • VS Code: Con extensiones oficiales de Dart y Flutter.
  • Android Studio: Necesario solo para las herramientas de compilación (Gradle) y emuladores.

0.2 Creación del Proyecto

El proyecto no se crea manualmente archivo por archivo. Utilizamos la CLI (Línea de Comandos) de Flutter para generar el esqueleto estándar ("Scaffold") recomendado por Google.

Comando Ejecutado (Anatomía del comando)

flutter create -t app --org com.liberto.melodyvault --platforms android,ios evaluacion_final

Hemos utilizado flags específicos para profesionalizar la estructura desde el segundo cero:

  • --org com.liberto.melodyvault: Define el "Domain Reverse Notation". Esto es crítico porque genera el applicationId en Android y el Bundle ID en iOS. Si no lo definimos ahora, cambiarlo después requiere tocar más de 15 archivos de configuración nativa y puede romper la vinculación con Firebase.
  • --platforms android,ios: Por defecto, Flutter crea carpetas para Web, Linux, Windows y MacOS. Al limitar las plataformas, mantenemos el proyecto limpio y reducimos el tiempo de indexado del IDE.
  • -t app: Especifica que estamos creando una aplicación final, no un plugin o un paquete.

Estructura de Carpetas Generada

  • /android & /ios: Contienen los proyectos nativos reales. Flutter simplemente "inyecta" su motor gráfico en estos contenedores. Aquí es donde configuramos permisos (cámara, internet) y certificados de firma.
  • /lib: El corazón del proyecto. Aquí vive el 100% de nuestro código Dart.
  • pubspec.yaml: El gestor de dependencias. Es el equivalente al package.json de Node.js o el pom.xml de Java. Aquí declaramos versiones exactas de librerías para evitar conflictos.
DEFENSA ORAL: "La elección de las banderas de creación no fue aleatoria. Al definir la organización y las plataformas desde el inicio, evitamos deuda técnica y aseguramos que el identificador único de la app sea coherente en todas las tiendas de aplicaciones."

BLOQUE 1: INFRAESTRUCTURA DE FIREBASE

En este bloque analizamos la fontanería invisible que conecta la app con la nube. No es solo "crear un proyecto", es configurar el entorno nativo compilado.

1.1 Configuración Nativa (Gradle & Info.plist)

Para que Firebase funcione en Android, necesitamos inyectar servicios de Google en el proceso de compilación de Gradle.

Archivo: android/app/build.gradle

Piensa en este archivo como el DNI o Pasaporte de tu aplicación. Define quién es la app (`applicationId`) y qué "idiomas" habla (versiones de Android).

Hemos elevado la minSdkVersion a **21** (Android 5.0 Lollipop) porque las librerías modernas de Firebase no soportan versiones anteriores (MultiDex issue). 

defaultConfig {
    applicationId "com.liberto.melodyvault.evaluacion_final"
    minSdkVersion 21
    targetSdkVersion flutter.targetSdkVersion
}

Archivo: ios/Runner/GoogleService-Info.plist

En iOS, este archivo actúa como el DNI de la aplicación. Contiene las claves API públicas que permiten a la app "presentarse" ante los servidores de Google Auth.

1.2 Índices Compuestos en Firestore

El Problema: Firestore indexa cada campo individualmente. Un filtro (`WHERE userId == ...`) y una ordenación (`ORDER BY createdAt`) requieren cruzar dos índices.

La Solución: Debemos ir a la pestaña "Indexes" en la consola y crear un índice compuesto (Composite Index) para los campos `userId` (Ascendente) y `createdAt` (Descendente).

DEFENSA TÉCNICA: "La creación de índices manuales demuestra que entendemos las limitaciones de rendimiento de las bases NoSQL. Sin el índice, la consulta requeriría escanear toda la colección, lo cual es O(N) en lugar de O(1)."

1.3 Reglas de Seguridad (Storage)

No podemos dejar el cubo de archivos abierto al mundo. Hemos configurado reglas en lenguaje CEL:

allow read, write: if request.auth != null;

BLOQUE 2: ARQUITECTURA DE DATOS (FIREBASE & MODELOS)

2.0 Filosofía NoSQL (Cloud Firestore)

A diferencia de una base de datos SQL tradicional (como MySQL) donde tenemos tablas rígidas y relaciones estrictas, Firestore es una base de datos NoSQL orientada a documentos.

  • Colecciones: Son contenedores (similares a carpetas) que agrupan documentos. Ejemplo: songs, users.
  • Documentos: Son objetos JSON flexibles. Cada documento puede tener campos diferentes, aunque en nuestra app forzamos una estructura coherente mediante código.
  • Escalabilidad: Elegimos Firestore porque escala horizontalmente. El tiempo de lectura de una consulta depende del tamaño del resultado, NO del tamaño total de la base de datos. Leer 10 canciones tarda lo mismo si hay 100 o 100 millones de canciones almacenadas.

2.1 Modelos como ODMs (Object Document Mappers)

Como Firestore devuelve JSON puro (`Map<String, dynamic>`), necesitamos una capa intermedia que transforme esos datos "crudos" en objetos Dart seguros y tipados. Los modelos en `lib/models/` son clases que actúan como contrato entre la Base de Datos (JSON) y la UI (Objetos).

2.1 Clase Song: Inmutabilidad y Serialización

La clase Song tiene todos sus campos final. Esto significa que una vez creada una instancia de una canción, no se puede modificar. Esta Inmutabilidad previene errores de estado (side-effects) difíciles de rastrear.

Serialización (fromFirestore / toFirestore)

No mezclamos la conversión de datos en las pantallas. La clase es responsable de saber cómo convertirse a sí misma. 

// Método de Fábrica (Constructor Nombrado)
factory Song.fromFirestore(DocumentSnapshot doc) {
  final data = doc.data() as Map<String, dynamic>;
  return Song(
    id: doc.id, // El ID no está en el JSON, viene del metadato del documento
    title: data['title'] ?? '', // Operador Null Coalescing para evitar NullPointers
    createdAt: (data['createdAt'] as Timestamp?)?.toDate() ?? DateTime.now(),
  );
}
DEFENSA: "Uso el operador ?? (Null Coalescing) exhaustivamente. Si la base de datos devuelve un nulo por error, la app NO crashea, sino que asigna un valor por defecto seguro (cadena vacía)."

Patrón copyWith

Como los objetos son inmutables (`final`), para "editar" una canción no cambiamos su título. Creamos un CLON de la canción antigua con el título nuevo. 

Song copyWith({String? title, String? artist...}) {
  return Song(
    title: title ?? this.title, // Si pasas null, mantengo el valor viejo
    artist: artist ?? this.artist,
    ...
  );
}

2.2 Clase Playlist: Relaciones Referenciales

En una base de datos Relacional (SQL) tendríamos una tabla intermedia `PlaylistSongs`. En NoSQL, optimizamos para lectura incrustando un array de IDs directamente en la playlist.

  • final List<String> songIds;: Solo guardamos las referencias, no duplicamos los datos de las canciones.
  • int get songCount => songIds.length;: Un "getter calculado" que nos da información derivada instantánea sin ocupar espacio en memoria.

BLOQUE 3: ARQUITECTURA DE SERVICIOS (BACKEND)

Entramos en el cerebro de la aplicación. Aquí la lógica es pura, sin contaminación visual de Widgets. Los servicios son la abstracción de la base de datos.

3.1 Patrón Singleton

El patrón Singleton es como la regla de la película Los Inmortales: "Solo puede quedar uno".

Aunque usamos `Provider` para inyectar servicios, internamente FirebaseFirestore.instance utiliza este patrón. Esto garantiza que solo haya una conexión de socket abierta con el servidor de Google, independientemente de cuántas veces llamemos a la base de datos. Eficiencia de memoria pura.

3.2 AuthService: Protocolo Auth

Este servicio encapsula FirebaseAuth. Su función crítica es mapear los errores crípticos de Firebase a un lenguaje humano. 

// auth_service.dart
Future<void> signIn(String email, String password) async {
  try {
    await _auth.signInWithEmailAndPassword(email: email, password: password);
  } on FirebaseAuthException catch (e) {
    if (e.code == 'user-not-found') throw 'No existe cuenta con ese email.';
    if (e.code == 'wrong-password') throw 'Contraseña incorrecta.';
    throw 'Error desconocido: ${e.message}';
  }
}

3.3 SongService: Mapeo de Streams

El método getSongs() es una tubería de datos viva. No pedimos los datos una vez; nos "suscribimos" a ellos.

Transformación de Datos (.map)

Stream<List<Song>> getSongs() {
  return _firestore.collection('songs')
      .orderBy('createdAt', descending: true)
      .snapshots() // FLUJO DE DATOS, NO FUTURE
      .map((snapshot) {
        return snapshot.docs.map((doc) => Song.fromFirestore(doc)).toList();
      });
}
DEFENSA: "¿Por qué .map?": Porque desacopla nuestra UI del formato JSON. Si mañana cambiamos de Firebase a SQL, solo cambiamos el servicio, no las pantallas.

3.4 PlaylistService: Gestión Relacional

Aquí manejamos la complejidad de relacionar entidades en NoSQL. Una Playlist guarda un array de strings `['songID1', 'songID2']`. Usamos `FieldValue.arrayUnion()` para añadir canciones, lo que garantiza que no haya duplicados (Set matemático) en la operación atómica de servidor.

3.5 MusicProvider: Orquestador de Estado

Los servicios (SongService, PlaylistService) son "tontos": solo saben traer datos crudos. La lógica de negocio real vive en MusicProvider.

  • Gestión de Carga (isLoading): Centralizamos el estado de carga aquí. Cuando empezamos a subir una canción, ponemos _isLoading = true y notificamos a la UI para que bloquee los botones.
  • Manejo de Errores (Error Handling): Si algo falla en el servicio, el Provider captura la excepción (`try/catch`), la guarda en una variable `_error` y la UI reacciona mostrando un SnackBar, sin crashear.

5.4 ForgotPasswordScreen

Una pantalla minimalista que llama a authService.sendPasswordResetEmail(email). Firebase se encarga de enviar el correo con el enlace mágico.

5.5 Persistencia de Sesión (AuthWrapper)

Una de las características más críticas de una app móvil es que el usuario no tenga que loguearse cada vez que abre la app. Esto se logra en el widget raíz AuthWrapper (en main.dart). 

class AuthWrapper extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    // Escucha activa del estado de autenticación
    final auth = context.watch<AuthProvider>();
    
    // Switch automático de pantallas
    if (auth.isAuthenticated) {
      return const HomeScreen();
    }
    return const LoginScreen();
  }
}
DEFENSA: "Este router dinámico reacciona en tiempo real. Si el usuario cierra sesión, `isAuthenticated` pasa a falso y la app lo expulsa inmediatamente a la pantalla de Login, sin necesidad de hacer `Navigator.push` manuales propenso a errores."

8.1 SongFormScreen

Pantalla unificada para Crear y Editar. Usa FilePicker para seleccionar archivos mp3 y jpg del almacenamiento local.

8.2 Subida Dual (Algoritmo de 3 pasos)

El proceso de guardar no es atómico.

  1. Paso 1: Subir Imagen a Firebase Storage -> Obtener URL `imgUrl`.
  2. Paso 2: Subir Audio a Firebase Storage -> Obtener URL `audioUrl`.
  3. Paso 3: Crear documento en Firestore con `{ title: ..., audio: audioUrl, image: imgUrl }`.

Todo envuelto en un bloque try/catch para gestionar fallos de red a mitad de subida.

BLOQUE 9: GESTIÓN CRUD Y CIERRE

El ciclo de vida del dato no termina en la creación. La gestión de la modificación (Update) y eliminación (Delete) es donde la mayoría de apps fallan. Aquí analizamos cómo MelodyVault maneja estas operaciones críticas.

9.1 Edición Inmutable ("The Update Problem")

Editar en Flutter es complejo porque los datos antiguos deben pre-llenar el formulario.

Paso de Argumentos

El constructor de `SongFormScreen` acepta un parámetro opcional `final Song? song`. En el initState, preguntamos: "¿Me han pasado una canción?". 

@override
void initState() {
  super.initState();
  if (widget.song != null) {
    // ESTADO DE EDICIÓN: Prelleno los controladores
    _titleController.text = widget.song!.title;
    _artistController.text = widget.song!.artist;
    // Guardo las URLs viejas por si el usuario no sube archivos nuevos
    _imageUrl = widget.song!.imageUrl;
  }
}
DEFENSA: "Esta técnica permite usar UNA SOLA pantalla para dos casos de uso (Alta y Modificación), reduciendo la base de código a la mitad y facilitando el mantenimiento."

9.2 Borrado en Cascada (Cascade Deletion)

Un error de novato es borrar el documento de la base de datos (`firestore.delete()`) pero dejar los archivos de audio e imagen en el Storage. Esto crea "archivos huérfanos" que ocupan espacio y cuestan dinero.

Nuestra Solución Robusta: Antes de borrar el registro en Firestore, capturamos las URLs de los archivos y ordenamos su destrucción en el Storage. 

Future<void> deleteSong(Song song) async {
  // 1. Borrar Ficheros Físicos (Limpieza)
  if (song.imageUrl.isNotEmpty) {
    await _storage.refFromURL(song.imageUrl).delete();
  }
  if (song.audioUrl.isNotEmpty) {
    await _storage.refFromURL(song.audioUrl).delete();
  }
  // 2. Borrar Registro Lógico
  await _firestore.collection('songs').doc(song.id).delete();
}

9.3 Widget Dismissible (UX de Deslizamiento)

Para el borrado, evitamos el típico botón "Papelera". Implementamos el patrón moderno "Swipe to Delete" usando el widget nativo Dismissible.

Anatomía del Deslizamiento:

  • Key: `Key(song.id)`. Esencial para que Flutter sepa qué elemento exacto de la lista se está animando. Sin esto, borraríamos el elemento equivocado.
  • Background: Un contenedor ROJO (`Colors.red`) con un icono de basura blanco alineado a la derecha. Esto da feedback visual inmediato de "Peligro/Borrado".
  • Direction: `DismissDirection.endToStart`. Solo permitimos deslizar de derecha a izquierda (estándar occidental).

Confirmación de Seguridad (confirmDismiss)

El deslizamiento es fácil de hacer por error. Por eso interceptamos la acción con confirmDismiss. 

confirmDismiss: (direction) async {
  return await showDialog(
    context: context,
    builder: (ctx) => AlertDialog(
      title: Text('¿Borrar canción?'),
      content: Text('Esta acción es irreversible y eliminará los archivos.'),
      actions: [
        TextButton(onPressed: () => Navigator.of(ctx).pop(false), child: Text('CANCELAR')),
        TextButton(onPressed: () => Navigator.of(ctx).pop(true), child: Text('BORRAR')),
      ],
    ),
  );
}

9.4 Gestión de Favoritos (Subcolecciones)

Para los favoritos, no usamos un array simple en el documento del usuario. Usamos el patrón de Subcolecciones. La ruta es: users/{userId}/favorites/{songId}.

¿Por qué Subcolecciones?

  • Rendimiento: Si un usuario tiene 5,000 canciones favoritas y usamos un array, tendríamos que descargar un documento gigante cada vez. Con subcolecciones, cargamos los favoritos bajo demanda.
  • Escalabilidad: Un documento de Firestore tiene un límite de 1MB. Una subcolección es infinita.

BLOQUE 10: OPTIMIZACIONES Y UX AVANZADA

Más allá de que "funcione", una app de 10 debe ser eficiente y agradable. Hemos implementado optimizaciones técnicas que marcan la diferencia.

10.1 Gestión de Memoria con CachedNetworkImage

Una app de música carga muchas carátulas. Si usáramos Image.network estándar, cada vez que hacemos scroll la app volvería a descargar la imagen, gastando datos y batería.

Solución: Usamos la librería cached_network_image. Esto guarda las imágenes en la caché local del dispositivo. Si el usuario vuelve a ver la misma canción, la carga es instantánea y offline. 

CachedNetworkImage(
  imageUrl: song.imageUrl,
  placeholder: (context, url) => ShimmerLoading(), // Efecto de carga elegante
  errorWidget: (context, url, error) => Icon(Icons.error),
),

10.2 Búsqueda Animada (AnimatedSearchBar)

En lugar de incrustar un campo de texto gigante que ocupa toda la AppBar, hemos creado un widget AnimatedSearchBar.

Al pulsar la lupa, el campo se expande con una animación suave (`AnimatedContainer` de 300ms). Esto es un uso avanzado de Animaciones Implícitas de Flutter, mejorando la percepción de calidad de la app.

10.3 Manejo de Estados Vacíos (EmptyStateWidget)

Una pantalla blanca es un error de diseño. Si no hay canciones, mostramos un EmptyStateWidget con un icono grande y una invitación a la acción ("¡Añade tu primera canción!"). Esto guía al usuario y evita la sensación de "app rota".

BLOQUE 11: CONCLUSIONES Y FUTURO

11.1 Conclusiones Técnicas

MelodyVault cumple estrictamente con la arquitectura Productor-Consumidor (Provider) y separa limpiamente la lógica de negocio (Servicios) de la interfaz (Widgets). Hemos priorizado la robustez (manejo de errores, modo offline con caché) y la Separación de Responsabilidades (Separation of Concerns): la UI solo pinta, el Provider gestiona el estado, y el Servicio habla con la nube.

11.2 Líneas Futuras de Desarrollo

Si el proyecto continuara, los siguientes pasos naturales serían:

  • Modo Offline Real: Descargar MP3s localmente (usando `sqflite` para persistencia).
  • Backend Cloud Functions: Mover el borrado de archivos al servidor para mayor seguridad.
  • Web Admin Panel: Una versión web en Flutter Web para administradores.
